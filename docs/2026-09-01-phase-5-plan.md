# Phase 5 plan: summary and tag generation (2026-09-01)

Agreed with the user before starting Phase 5. `CLAUDE.md` remains the source of truth for product
and architecture; this records the decisions it does not cover and the order the work should
happen in.

Scope per `CLAUDE.md` Phase 5: **summary generation, tag generation.**

---

## 1. Why an LLM, and why now

`CLAUDE.md` closes with "Do not blindly add technology because it appears in the architecture
diagram", and an LLM provider appears nowhere in it at all. So this gets the "Important Rule"
treatment in full.

**What problem it solves.** The product's promise is "save, forget, describe, find". Finding by
description needs the bookmark to hold *what the page is about*, in words the user might later
reach for. Extraction gives us what the page says about itself — an `og:description` written by a
marketing team, or nothing. Tags give the user a navigable axis, but only if they exist, and
nobody tags their own bookmarks. Phase 6 then embeds this text: a bookmark whose only content is
its title embeds badly, so weak enrichment caps the ceiling on semantic search a phase later.

**Why the current architecture is insufficient.** Nothing in the pipeline produces language. The
metadata worker copies fields out of HTML; it cannot condense, and it cannot name a topic the page
never names. `summary` and `tags` exist on the `Link` model and are permanently empty for every
link nobody hand-edited.

**Alternatives considered.**

- *Classical keyword extraction — TF-IDF, RAKE, YAKE, KeyBERT.* Cheap, offline, no provider, no
  per-link cost. Rejected on output quality for this specific job: these return salient **phrases
  from the source text**, so a page about Redis returns `redis`, `cache`, `key`, `expiry` — the
  words already in the title. They cannot produce `performance` for a page that never says it, and
  they have no notion of an existing vocabulary to reuse, which §3 shows is the whole problem. They
  also cannot summarise at all, so summary generation would need a second mechanism regardless.
- *Extractive summarisation — first N sentences, TextRank.* Free, and it never hallucinates, which
  is a real advantage given §4. Rejected because the extracted sentences are the page's own framing
  at its own length; it is not a description in the user's terms, which is what the search
  experience is built on.
- *A local model via Ollama.* No per-link cost and no data leaving the machine. Rejected for now on
  operational cost: it is a second runtime, a multi-gigabyte model, and a GPU question, introduced
  for a workload measured in cents. Revisit at Phase 9 if per-link cost turns out to matter at real
  volume — the interface in §7 keeps the provider swappable.
- *Defer enrichment to Phase 6 and let embeddings carry search.* Tempting, since embeddings do the
  semantic work. Rejected because the embedding input is exactly this text: `CLAUDE.md`'s Semantic
  Search section lists summary and tags as primary embedding inputs. Skipping Phase 5 makes Phase 6
  embed titles.

**Why this is appropriate.** The task is single-call summarisation and classification over short
text — the simplest tier there is, no agent loop, no tools, no state. It is the one job where an
LLM is straightforwardly better than the alternatives, and §3 needs semantic judgment that no
classical method has.

## 2. Model — decided: Claude Sonnet 5

`claude-sonnet-5` through the official `@anthropic-ai/sdk`. Chosen by the user with the cost table
in front of them.

Roughly 1,200 input tokens (system prompt + tag vocabulary + title and description) and ~150
output per link:

| Model | Per link | Per 1,000 links |
| --- | --- | --- |
| Claude Opus 5 | ~$0.010 | ~$10 |
| **Claude Sonnet 5** | **~$0.004** | **~$4** |
| Claude Haiku 4.5 | ~$0.002 | ~$2 |

The Batch API halves any of these, and enrichment is already asynchronous — but batch latency runs
minutes to hours, which is wrong for a link the user just saved and is looking at. **Batch is the
right tool for a backfill, not for the live path.** Keeping the call behind one function (§7) means
a backfill script can route the same prompt through batching later without touching the worker.

**API details that are easy to get wrong**, recorded because they cost time otherwise:

- **`temperature` is removed on Sonnet 5 and returns a 400.** The instinct on a classification-ish
  task is `temperature: 0` for determinism. It is not available; do not send it.
- **`budget_tokens` is removed and returns a 400.** Use `output_config: { effort: "low" }` — this
  is a short, bounded task and `low` is the documented setting for it.
- **Assistant prefill returns a 400.** Constrain the output with structured outputs instead —
  `output_config: { format: {...} }` — and prefer `client.messages.parse()` so the response is
  validated against the schema rather than hand-parsed.
- `max_tokens` around 1024. The output is a short summary plus five tags; streaming is unnecessary
  at that size.
- Prompt caching is unlikely to trigger: the minimum cacheable prefix is 512–4096 tokens depending
  on model, and our system prompt is well under it. Do not design around it.
- Catch a **chain** of typed SDK errors, most specific first, not one broad class — the retry
  classification in §9 depends on telling 429 and 5xx apart from 400.

`ANTHROPIC_API_KEY` goes in `.env`, already gitignored, and into `.env.example` as an empty
placeholder. With no key set, enrichment must **disable itself cleanly** — the same shape as
`ENABLE_METADATA_WORKER=false` — so a fresh clone runs the whole product without an account.

## 3. Tag consistency — vocabulary in the prompt, not similarity matching

The user raised the right problem: **vocabulary drift.** Generate tags per link independently and
within fifty links there are `js`, `javascript`, `JavaScript`, `node`, `nodejs`, `api`, `apis`. The
sidebar becomes unusable, `$all` filtering silently misses links, and a tag stops being something
you can navigate by.

The user's first proposal was to embed each candidate tag, match it against existing tags by cosine
similarity, and reuse above a threshold. **Rejected, for a specific reason rather than a vague one:
short-string embeddings measure topical relatedness, not synonymy, and those are different axes.**

| Pair | Similarity | Should merge? |
| --- | --- | --- |
| `postgres` / `postgresql` | high | **yes** |
| `react` / `vue` | high | **no** — different tools |
| `ml` / `machine-learning` | moderate — abbreviations embed poorly | **yes** |
| `css` / `tailwind` | high | **no** |

No threshold separates those. High enough to keep `react` and `vue` apart and it misses
`ml`/`machine-learning`; low enough to catch the abbreviation and every Vue link is now tagged
`react`. The failure is **silent and irreversible** — nothing tells the user it happened.

**Decided instead: constrained generation.** The user's existing tags go into the prompt, and the
model is told to reuse one whenever it genuinely fits and to propose a new tag only when nothing
does. The model knows postgres and postgresql are the same thing and react and vue are not; that is
semantic knowledge, not vector proximity. One call, one system, no threshold to tune, and it
produces the summary in the same request.

Cost is negligible — 300 tags is roughly 900 prompt tokens. The vocabulary comes from the existing
`listTags(userId)` aggregation, so **no `Tag` collection is introduced.**

**The similarity idea becomes correct again at scale, in a different role.** Past roughly a thousand
tags the vocabulary stops fitting comfortably, and embeddings should then shortlist the ~50 most
plausible candidates to show the model. That is the right division of labour — **embeddings for
recall, the model for the judgment call** — and it lands naturally in Phase 6, when embeddings exist
for their own reasons. Not now.

Two deterministic guards around the call, independent of the model:

- **Normalise before storing** — lowercase, collapse whitespace to hyphens, strip trailing
  punctuation, drop anything over the 40-character schema limit, cap at five tags per link.
- **Case-insensitive snap** — before inserting a tag, match it against the existing vocabulary
  case-insensitively and adopt the existing casing. Drift cannot happen even if the model slips.

**No auto-singularisation.** It breaks `ops`, `docs`, `aws`, `k8s` and buys little.

## 4. What the model sees — title and description only

**Decided by the user: no page text.** The extractor keeps only title, description, author,
thumbnail and favicon; the HTML is streamed, parsed and discarded. Storing a cleaned excerpt was
offered and declined, so enrichment works from what the `Link` already holds.

The consequence, stated plainly: **for pages with a thin or absent `og:description`, the summary
will be weak, and for some it cannot exist at all.** Where the description is good, the summary
will largely restate it. Tags fare better — a title like "Redis Caching Strategies" carries enough
to produce `redis`, `caching`, `performance` — so tag quality is affected far less than summary
quality.

Two rules follow, and neither is optional:

- **Never invent.** The model is instructed to return an **empty summary** when the input does not
  support one, rather than guessing from the URL or the domain. A hallucinated summary is worse
  than no summary here: it is shown to the user as fact, and Phase 6 embeds it, so an invented
  sentence actively corrupts search.
- **Do not call the API with nothing.** If the description is empty and the title is absent or is
  merely the domain, skip the request entirely and mark the link enriched with no summary. This
  saves money and removes the strongest temptation to invent.

**The decision is reversible and cheap to reverse.** Build the prompt from a single
`buildEnrichmentInput(link)` function. If summaries prove too thin in use, capturing an excerpt in
the metadata worker becomes a change to that one function plus a schema field — the worker, the
events and the retry logic are untouched.

## 5. Schema additions to `Link`

All additive. `tags` keeps its type, so **every existing index, the text index and the `$all`
filters keep working untouched** — there is no migration.

- `summary` — already exists, nothing writes it yet. Now written. Target one or two sentences; the
  2000 limit stays a ceiling, not a goal.
- `autoTags: [String]` — what the model produced, kept apart from the effective set.
- `tagsEditedByUser: Boolean` — see §6.
- `enrichmentStatus` — `pending | queued | processing | done | skipped | failed`, default
  `pending`. `skipped` is a real terminal state: no API key configured, or §4's nothing-to-work-
  with case.
- `enrichmentAttempts`, `enrichmentError`, `enrichmentStartedAt`, `enrichedAt` — the same lease and
  retry bookkeeping the Phase 4 fields carry, for the same reasons.

## 6. Provenance — auto-tags must never fight the user

Phase 3 set the precedent: extraction fills only fields the user left empty, so typed values are
never overwritten. Tags need the same guarantee, but a tag set is not a scalar and the naive rule
breaks.

The scenario that will bite: a user deletes an auto-tag they dislike, the link is re-enriched
later, and **the tag comes back**. That is infuriating, and it is the fastest way to make someone
turn the feature off.

**Rule: once `tagsEditedByUser` is true, enrichment writes the summary and never touches tags
again.** `PATCH /api/links/:id` sets the flag whenever the request changes `tags`. `autoTags`
records what the model produced, so the two can be told apart in the UI and in any future backfill.

This is deliberately the small version. If re-enrichment ever becomes routine — a model change, a
corpus-wide backfill — the upgrade is a `dismissedTags` suppression list subtracted at the end. Not
built now; one boolean covers the actual Phase 5 behaviour.

## 7. Where it runs

A new consumer, and **nothing in Phase 4 changes.**

```
metadata.extracted ──► enrichment worker ──► MongoDB (summary, autoTags)
                              │
                              ├─► link.enriched          (Phase 6 consumes)
                              └─► link.processing.failed
```

- `src/services/enrichment.js` — prompt construction and the provider call, behind
  `enrichLink({ title, description, vocabulary })`. This is the only file that imports the
  Anthropic SDK, which is what makes §1's "revisit a local model at Phase 9" a real option rather
  than a slogan.
- `src/workers/enrichmentWorker.js` — consumes `metadata.extracted`, claims, calls, writes back.
- `link.enriched` joins `topics.js`. It is named in `CLAUDE.md` and has been deliberately absent
  until it had a producer; now it has one.
- The reaper extends to sweep `enrichmentStatus: 'pending'` and to reclaim expired enrichment
  leases. Phase 4's lesson holds unchanged: a Kafka message can be lost, and the database sweep is
  what recovers it.

Both workers run in the same worker process. Splitting them is a scaling decision with no evidence
behind it yet, and Phase 4 already proved the process boundary works.

## 8. Enrichment failure must not fail the link

**A link whose enrichment failed is still a perfectly good bookmark.** It has a title, a favicon and
a URL, and it opens. Marking it `failed` would show the user a broken bookmark that works fine.

So `enrichmentStatus` is a **separate field** from `processingStatus`, and a link reaches `ready` on
extraction alone. The dashboard shows the summary and auto-tags when they arrive and shows nothing
where they have not; there is no error state in the link list for a failed enrichment. Retry is the
reaper's job, not a button.

## 9. Failure handling, idempotency and cost

**Idempotency matters more here than in Phase 4, because a redelivered event costs real money.** The
handler checks `enrichmentStatus` and returns immediately for anything already `done` or `skipped`.
The claim is the same atomic `findOneAndUpdate` the Phase 4 queue uses.

Retry classification, mirroring Phase 3's policy and its Phase 4 correction:

- **Retryable** — 429, 5xx, connection errors, timeouts. Back off and retry, three attempts.
  Phase 4's third bug was a timeout misclassified as permanent; do not repeat it.
- **Permanent** — 400 and 404. Fail immediately; retrying a malformed request cannot help.
- **Skipped, not failed** — no API key, or nothing to work with per §4.

A user pasting 500 links means 500 API calls. For Phase 5 the bound is the consumer's existing
concurrency of three plus retry backoff, which spreads the load. **A real per-user cost ceiling is
not built here** — it is Phase 7's rate limiting, and this is one of the places where that phase
earns its keep rather than existing for the sake of Redis.

## 10. Tag rename and merge — in scope

One endpoint, `PATCH /api/links/tags/:name`, doing an `updateMany` scoped by `userId`. Renaming to a
tag that already exists **is** the merge; deduplicate the array afterwards. Plus a rename affordance
in the tag sidebar.

This is in Phase 5 rather than deferred because it is what makes imperfect auto-tags tolerable. It
converts any drift the model creates from a permanent corruption of the user's vocabulary into a
two-second fix on the user's own terms. In a product people actually use, that is worth more than
squeezing the last few percent out of the matching logic — and it is the honest hedge against §3
being wrong.

## 11. Testing

The Phase 4 lesson stands: **the unit tests keep passing while the real dependency misbehaves.**

- The provider call is faked in tests. No suite run may spend money or need a network.
- Tested without the network: normalisation and case-snapping, vocabulary assembly, the
  `tagsEditedByUser` guard, the skip conditions from §4, idempotent redelivery, the claim and lease
  cycle, the retry classification, and rename/merge including the dedupe on collision.
- **Then run it against the real API** on a set of genuinely varied links — a good `og:description`,
  an empty one, a title that is only a domain, a non-English page, a non-HTML content type — and
  read the output. §4 means summary quality is the risk of this phase, and no unit test can see it.
- Verify a redelivered event does not produce a second billed call, checked against real usage
  rather than against a mock.

## 12. Step plan

1. **Schema and config.** The §5 fields, `ANTHROPIC_API_KEY` in `.env.example`, and the clean
   disable path when no key is set. Tests first for the guard and the skip conditions.
2. **`services/enrichment.js`** — prompt construction, structured output, typed-error
   classification. Verified against the real API in isolation before any worker exists, the same way
   the Phase 4 broker was smoke-tested first.
3. **Normalisation and case-snapping**, with the vocabulary assembled from `listTags`. Pure
   functions, fully tested.
4. **The enrichment queue** — claim, lease, attempts, terminal states — reusing the `linkQueue`
   shape rather than reinventing it.
5. **`workers/enrichmentWorker.js`** consuming `metadata.extracted`; `link.enriched` added to
   `topics.js` and published at the terminal transition.
6. **The reaper extension** for `enrichmentStatus: 'pending'` and expired enrichment leases.
7. **`tagsEditedByUser`** wired into `PATCH /api/links/:id`.
8. **Tag rename/merge** — endpoint, then the sidebar affordance.
9. **Dashboard** — show the summary on the card, and distinguish auto-tags from user tags.
10. **Verification** — the §11 real-API run on varied links; a redelivery check; and enrichment
    failing while the link stays usable.

## 13. Not in Phase 5

Embeddings and the Python service (Phase 6), Redis and rate limiting (Phase 7), hybrid search
(Phase 8). Also deliberately out: a `Tag` collection, tag hierarchies, per-user prompt
customisation, batch-API enrichment, and content-type tags (`video`, `tutorial`) — the last is
plausibly a separate field rather than a tag, and there is no evidence for it yet.

## 14. Revisit after this phase

- **Automatic collection allocation.** Deferred in Phase 4 §12 precisely until real auto-tags
  existed to judge against. They will now. The agreed ladder: suggest-only from tag overlap →
  suggest from embedding similarity to a collection centroid (Phase 6) → auto-assign above a
  threshold, opt-in and reversible. Collections stay manual in Phase 5, confirmed again by the user.
- **Summary quality under §4's constraint.** If summaries read as restatements of the description,
  the fix is the excerpt, and §4 keeps it cheap.
- **Whether the vocabulary still fits the prompt** for the heaviest user. The trigger for §3's
  embedding shortlist is a measured token count, not taste.
