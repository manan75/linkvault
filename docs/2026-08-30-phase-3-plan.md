# Phase 3 plan: metadata extraction and the UI pass (2026-08-30)

Agreed with the user before starting Phase 3. `CLAUDE.md` remains the source of truth for
product and architecture; this records the decisions it does not cover and the order the work
should happen in.

Scope per `CLAUDE.md` Phase 3: **URL metadata extraction, processing status, error handling.**
Folded in at the user's request: **the UI/UX pass**, so the visual work lands together with the
content that makes it worth doing rather than as a separate phase.

---

## 1. Why the UI work belongs in this phase

The dashboard reads as bland largely because every row is text on white. Phase 3 supplies
favicons, real titles, descriptions and thumbnails — the things that make a list look designed.
Doing the visual pass before that content exists would mean tuning a layout around placeholder
rows and redoing it once extraction lands.

So the two halves are deliberately interleaved: theme tokens and the row redesign go in early
(everything after is then built in tokens), and the parts that display fetched content are built
once there is fetched content to display.

## 2. Theming: what is in and what is out

**In:**

- **Dark mode, tri-state** — System / Light / Dark, not a boolean. System is the default and
  follows the OS.
- **Accent colour picker** — 6 preset swatches. Accent only: buttons, the active sidebar item,
  focus rings, the favourite star. Not backgrounds, not text.

**Out, decided and not to be revisited this phase:**

- Free background colour picker and gradients. An arbitrary user-chosen background cannot be
  guaranteed to keep muted metadata text readable, and a gradient behind a dense list of cards
  reads as busy — the opposite of the stated goal. Curated surface tones were offered as the
  safe version of this and were not taken up.
- Photo/image themes, including the Notion-style header banner.

**Preference storage: `localStorage`.** Instant, paints correctly on the first frame, no backend.
It does not follow the user to another device; that is accepted. Keep every read and write behind
a single `usePreferences` hook so moving to `User.preferences` later touches one file.

Applying the theme needs a small inline script in `index.html` that sets `data-theme` on `<html>`
**before** React mounts. Without it there is a visible flash of the light theme on every load for
dark-mode users.

## 3. Favicons and thumbnails are hotlinked

The stored `favicon` and `thumbnail` URLs are put straight into `<img src>` and the browser
fetches them from the origin site.

The trade, stated plainly: rendering the dashboard sends a request to every site represented in
the list, so those sites can infer that someone at that IP is looking at a page referencing them.
This is the same exposure a browser bookmark bar already has. Proxying through the API would close
it but adds an endpoint, a second SSRF surface, and wants a cache — which really wants Redis, and
Redis is Phase 7. Revisit it there if it still matters.

Consequence for validation: because these URLs end up in `src` attributes, extraction must reject
any favicon or thumbnail that is not `http:` or `https:`. A stored `javascript:` URL would be a
stored XSS vector.

## 4. Fetched metadata never overwrites what the user typed

This closes the open question carried since Phase 1. Expected answer confirmed: **user input wins.**

Implementation is the cheap version — **extraction only fills a field that is currently empty.**
No `titleSource` column, no edit tracking. A user who has typed a title has made it non-empty, so
extraction skips it.

Known limitation, accepted: if a "refresh metadata" action is added later, this rule cannot tell a
user-typed title from a previously extracted one, so a refresh would not update anything already
populated. If that action lands, upgrade to a `userEdited: [String]` array on `Link` listing the
fields the user has touched, and have extraction skip exactly those.

## 5. How extraction runs before Kafka exists

This is the one architectural decision in the phase, so it gets the `CLAUDE.md` "Important Rule"
treatment.

**The problem.** Architecture Principle 2 says saving a URL must not wait for metadata extraction.
Fetching a page takes seconds. Kafka and real workers are Phase 4, and Principle 1 says not to
introduce infrastructure before it has a purpose. Phase 3 therefore needs something in between.

**Why the current architecture is insufficient.** Today `POST /api/links` writes a row and returns.
Nothing ever moves a link off `processingStatus: 'pending'`, because nothing processes anything.

**Alternatives considered.**

- *Extract synchronously inside the request.* Directly violates Principle 2. The save box would
  hang for seconds on a slow site and fail outright on a dead one. Rejected.
- *Fire-and-forget after responding* (a floating promise or `queueMicrotask`). Five lines, and
  genuinely tempting. Rejected because the work is lost if the process exits between the response
  and the fetch finishing — which in development with `node --watch` happens on every file save,
  leaving links stuck at `pending` with nothing to pick them up. It also gives retries nowhere to
  live, and Principle 5 requires retries.
- *Introduce Kafka now.* Violates Principle 1, and pre-empts the still-open Phase 4 question about
  which language the workers are written in.

**The choice: an in-process poller that claims pending links from MongoDB.**

- Claim atomically, so two loops can never take the same link:
  `findOneAndUpdate({ processingStatus: 'pending' }, { $set: { processingStatus: 'processing', processingStartedAt: new Date() } }, { sort: { savedAt: 1 }, new: true })`
- Run on a short interval (~2s) with a small bounded concurrency (~3). Optionally nudge the loop
  on save so processing feels immediate rather than up to 2s late.
- Reclaim stale leases: anything left in `processing` beyond a few minutes goes back to `pending`,
  or to `failed` once attempts are exhausted. This is what makes a crash mid-fetch recoverable.
- Live in `server/src/workers/`, started from `index.js` behind an env flag
  (`ENABLE_METADATA_WORKER`) that is **off in tests** — a background poller running during the
  suite would make tests non-deterministic.

**Why this is appropriate rather than throwaway.** The claim → process → complete/fail state
machine is exactly what a Kafka consumer does. Phase 4 replaces the *trigger* (poll becomes
consume) and keeps the extraction logic, the retry policy and the status transitions untouched.
Principle 4 wants idempotent workers, and claiming by status gives that for free: replaying the
same link is safe because a link not in `pending` is not claimed.

One consequence worth naming now: writing the extractor in Node this phase makes "keep the
non-embedding workers in Node" the path of least resistance for Phase 4's open language question.
That is a nudge, not a commitment.

## 6. The one rule to not get wrong: fetching URLs a stranger chose

Phase 2's rule was scoping every query by `userId`. Phase 3's is that **the API is about to make
HTTP requests to addresses the user controls, from inside the trust boundary.**

Left unguarded this is a server-side request forgery primitive: a user saves
`http://169.254.169.254/latest/meta-data/`, `http://127.0.0.1:27017`, or `http://10.0.0.5/`, the
API fetches it, and stores the result in a field they can read straight back. That is an internal
network read, and on a cloud host it is cloud credentials.

Non-negotiable, all of it in **one** guarded fetch client that no route may bypass:

- **Resolve the hostname, then check every resolved address** against loopback, private
  (`10/8`, `172.16/12`, `192.168/16`), link-local (`169.254/16`), CGNAT (`100.64/10`), `0.0.0.0`,
  `::1` and unique-local IPv6 (`fc00::/7`). Checking the hostname string is not enough.
- **Re-check on every redirect hop.** A perfectly public URL is allowed to `302` to
  `169.254.169.254`. Cap redirects at 3.
- Ideally **connect to the address that was checked**, closing the DNS-rebinding window between
  the check and the connection.
- **Total timeout** around 8s. **Response size cap** around 2 MB, enforced *while streaming* — a
  cap applied after download does not prevent memory exhaustion.
- **Content-type must be HTML.** Anything else is recorded as processed-with-nothing, not parsed.
- **Parse, never execute.** An HTML parser only — no headless browser, nothing that runs page
  scripts. `CLAUDE.md` states this outright.
- **Sanitise everything stored**: strip control characters, collapse whitespace, cap to the schema
  maxima, and reject non-`http(s)` favicon and thumbnail URLs (see section 3).

Tests should assert refusal for a private address **and** for a public URL that redirects to one.

## 7. Failure handling

Principle 5 lists the failures; the policy is:

- **Transient** — timeout, DNS temporary failure, connection reset, `429`, `5xx`. Retry with
  exponential backoff, maximum 3 attempts, then `failed`.
- **Permanent** — `400`/`401`/`403`/`404`/`410`, blocked address, non-HTML content type, unparseable
  document. Straight to `failed`, no retry. Retrying these only wastes attempts.

One bad URL must never stop the loop: every iteration is individually guarded and logs the link id
with the error. A site being down is normal operation, not an incident.

## 8. Schema additions to `Link`

Each one justified, per "do not over-engineer the schema prematurely":

- `author` — `CLAUDE.md` asks for "extract author when available" under URL Processing, but the
  `Link` model it specifies has no field to put it in. **This is a genuine gap in `CLAUDE.md`**,
  not an addition of ours; flag it to the user and add the field.
- `processingAttempts` (Number, default 0) — the retry policy needs somewhere to count.
- `processingError` (String) — a short, user-safe reason, shown next to the retry action.
- `processingStartedAt` (Date) — required for stale-lease reclaim.
- `processedAt` (Date) — when extraction last completed.

Deliberately **not** added: anything for summaries, tags or embeddings. Those are Phases 5 and 6
and the fields already exist.

## 9. Extraction precedence

Per field, first match wins:

- **title** — `og:title` → `twitter:title` → `<title>` → fall back to the domain
- **description** — `og:description` → `twitter:description` → `<meta name="description">`
- **author** — `<meta name="author">` → `article:author` → JSON-LD `author`
- **thumbnail** — `og:image` → `twitter:image`
- **favicon** — `<link rel="icon">` / `apple-touch-icon` → `/favicon.ico` fallback

Resolve every relative URL against the **final URL after redirects**, not the URL the user pasted.

**`<link rel="canonical">` is deliberately ignored.** It is tempting to feed it back into
`canonicalUrl`, but that field is the unique index and the Phase 4 idempotency key — rewriting it
after the fact could collide with an existing bookmark or silently change a link's identity. If it
is ever wanted, it belongs in its own decision.

Parser: add **`cheerio`** — well understood, and it does not execute scripts. (`node-html-parser`
is the lighter alternative if the dependency weight matters.) This is the phase's one new
dependency and it earns its place; hand-rolled regex over HTML does not survive real pages.

## 10. Step plan

Ordered so that each step is independently verifiable and nothing is built twice.

1. **Theme tokens and dark mode.** CSS custom properties for surface, text, border and accent;
   `data-theme` on `<html>`; the anti-flash inline script. Replace hardcoded `slate-*` utilities.
   Pure refactor — no behaviour change, and the diff should prove it.
2. **Accent picker and `usePreferences`.** Six swatches, a small settings popover in the header,
   `localStorage` behind the hook.
3. **Link row redesign.** Density pass, drop the raw `canonicalUrl` line, title/metadata hierarchy,
   icon actions on hover (star stays visible, it is state), read state as a border or dot rather
   than opacity, skeleton rows while loading. Leaves space for a favicon and thumbnail that do not
   exist yet.
4. **Schema additions** from section 8, including `author`.
5. **The safe fetch client** from section 6, with its own unit tests. Security-critical and
   testable in isolation — build and test it before anything depends on it.
6. **The metadata parser** from section 9, with unit tests against saved HTML fixtures (a rich
   OG page, a bare page with only `<title>`, a page with relative favicon and image paths, and
   malformed markup).
7. **The worker loop** from section 5: claim, process, complete, fail, stale reclaim, retry policy.
   Tests drive it directly rather than waiting on an interval.
8. **Status through the API and into the UI.** Pending shows a subtle shimmer; `failed` shows the
   reason and a retry action; favicons and thumbnails appear in the row built in step 3.
9. **Manual browser pass**, light and dark, against real URLs — including a deliberate 404, a site
   with no OG tags at all, and a slow page — plus a private-address URL to watch it be refused.

## 11. Not in Phase 3

Kafka and separate worker processes (Phase 4), summary and tag generation (Phase 5), embeddings and
semantic search (Phase 6), Redis caching (Phase 7). On the UI side: grid/gallery view, surface
tones, image or banner themes, and any `rel="canonical"` rewriting.

## 12. Still open after this phase

1. **Worker language split** — needed before Phase 4, and section 5 notes this phase nudges the
   answer toward Node for everything except the embedding worker.
2. **Vector search in local dev** — Atlas Local container or a real Atlas cluster. Needed before
   Phase 6.

Both are architectural and deserve the `CLAUDE.md` "Important Rule" treatment when they come up.
