# Deploy v1: hardening (2026-09-02)

What shipped from the "Deploy v1" half of
[the deployment plan](./2026-09-02-deployment-and-extension-plan.md), the decisions taken while
building it, and what was verified. The code is done; the provisioning is not, and section 6 is the
handover for it.

Scope: steps 1 to 6 and 9 of the plan's order of work. Steps 7, 8 and 10 (Atlas, Render, Vercel,
the cron ping) are dashboard work and are listed here rather than done.

---

## 1. The cookie: `sameSite: 'none'`, not the Vercel rewrite

**Decided by the user, against the plan's recommendation**, and the plan's fallback becomes the
primary. `server/src/config/cookies.js` now sets `sameSite: 'none'` with `secure: true` in
production and keeps `lax` in development, where the Vite proxy makes everything same-origin
anyway.

What this buys: no proxy hop, no dependence on Vercel's rewrite quotas, and one less moving part
between the browser and the API. **The plan's open question 3 — whether Vercel Hobby permits and
meters external rewrites — is closed as no longer applicable.**

What it costs, stated plainly because it will be noticed eventually:

- **The session is now a third-party cookie.** Safari blocks those by default, so **login will not
  work in Safari or any iOS browser.** v1 is deliberately Chrome-first; the user confirmed this
  when choosing the approach, and the extension being planned is Chrome-only regardless.
- **CORS became load-bearing.** With the rewrite, the browser only ever talked to Vercel and CORS
  was a formality. Now `CLIENT_ORIGIN` is the only thing standing between the API and any page on
  the internet reading a signed-in user's bookmarks. It must be the exact Vercel origin — scheme
  included, no trailing slash — and `credentials: true` means it can never be `*`.
- **Vercel preview deployments will not be able to log in**, because each gets its own URL and only
  the production origin is allowed. Fixable with an origin pattern if previews start mattering.

The Bearer-token path (plan §10) is what removes all three, and it stays where the plan put it:
after Phase 6.

`client/src/lib/api.js` now reads `VITE_API_BASE`, falling back to `/api`. Unset locally, so the
dev proxy path is untouched; set on Vercel to the Render URL **including `/api`**.

## 2. Registration stays open, so the caps had to do the bounding

The user chose open registration with stricter caps. That choice propagates further than it looks,
and two things came out of taking it seriously.

**Account creation is now the way past every per-user quota.** A per-user link cap bounds nothing
if users are free to mint. So registration is limited to **5 per hour per IP** — tighter than the
plan's 10 per 15 minutes — while login keeps 10 per 15 minutes for brute-force protection. Five an
hour is invisible to a person and ruinous to a script.

**The two limits that bound money had to be moved out of the rate limit store.** This is the more
important consequence. The memory store loses its counters on every restart, and Render restarts
the process on every deploy and after every idle spin-down. A daily spending ceiling that resets
whenever the app goes quiet is not a ceiling. So the limits are split by what they are for:

| Limit | Value | Where it lives | Why there |
| --- | --- | --- | --- |
| Login attempts | 10 / 15 min / IP | Memory store | A throttle. Losing it on restart is survivable. |
| Registrations | 5 / hour / IP | Memory store | Same. |
| Link saves | 20 / hour / **user** | Memory store | Same. Keyed by account because the cost is billed per account. |
| Bookmarks per user | 100 | **MongoDB** (`countDocuments`) | Must be exact at the moment of the write. |
| Enrichment per day | 200, global | **MongoDB** (`DailyUsage`) | Bounds real money. Must survive every restart. |

`services/usage.js` owns both durable ones. The daily counter is a single document per day keyed
`enrichment:<YYYY-MM-DD>`, incremented with a conditional upsert: the filter refuses to match a
counter already at the limit, so the increment either happens or does not, atomically. When the
filter matches nothing and the document exists, Mongo raises `E11000` — which is not an error here,
it is the answer.

## 3. Three things the ceiling turned out to need

**A new terminal state would have been wrong, so `deferEnrichment` exists instead.** The obvious
implementation reuses `skipEnrichment` when the budget is spent. That is a bug: `skipped` is
terminal and means "there is nothing here worth summarising", which stays true forever, whereas a
spent budget is a condition of today. Skipping would permanently abandon a queue that merely needed
to wait until midnight. `deferEnrichment` puts the link back to `pending` **and gives the attempt
back**, because the retry ladder exists to stop hammering something that is failing and this link
has not been tried.

**The reserve has to sit after the claim.** Before it, a redelivered event would consume budget for
work it was never going to do. After the claim and after the `hasEnoughToEnrich` check, exactly one
reservation happens per link that will actually be enriched.

**The ceiling had to be enforced on the producer side too.** With only the worker refusing, an
exhausted budget does not stop anything — it moves the refusal one stage later, and every link
awaiting enrichment cycles through publish, claim, refuse and release on each lease expiry, burning
database writes all night to rediscover the same answer. The reaper now takes a
`hasEnrichmentBudget` predicate and simply does not publish. It is injected rather than imported so
the reaper still knows nothing about what enrichment costs, and it logs on the transition rather
than on every two-second sweep.

## 4. Shutdown, and why it got its own module

The plan called `shutdown()` incomplete. It was: it stopped the reaper and the bus and called
`process.exit(0)`, never closing the HTTP server, never disconnecting MongoDB, and never stopping
either worker. **Render sends SIGTERM on every deploy**, so that was wrong routinely rather than
exceptionally — a link being fetched or summarised at that moment kept its claim and had to wait
for the stale-lease sweep.

Now: reaper first (the only producer, so the backlog stops growing), then the HTTP server, then
both workers drained, then the bus, then MongoDB last because everything above it writes to it.
A timeout backstop exits anyway if any step hangs, because Render follows SIGTERM with SIGKILL
regardless.

Three things worth recording:

- **`server.close()` alone hangs.** It stops accepting new connections but waits for open ones, and
  an idle keep-alive connection waits out its own timeout. `closeIdleConnections()` is what makes
  the close actually happen; without it every shutdown runs to the backstop.
- **`workers/drain.js` is what makes "stop" mean something.** A worker tracks in-flight handler runs
  and refuses new ones once draining. Refusing is free: the link is still `pending`, so the next
  process's first sweep republishes it.
- **The worker entrypoint had the identical bug**, so the mechanism moved to `utils/shutdown.js` and
  both entrypoints use it. What differs between them — which things stop, in what order — stays in
  the entrypoint as a list, which is the part worth reading.

## 5. Smaller decisions

- **`ENABLE_REDIS=true` fails at startup** rather than silently using memory. The store is a seam
  waiting for its Phase 7 implementation; falling back quietly would hide a misconfiguration whose
  only symptom is limits that are not shared.
- **`helmet` with `crossOriginResourcePolicy: 'cross-origin'`.** Its `same-origin` default is
  written for an app that serves its own assets, which this one deliberately does not.
- **`engines: node 22.x`** pinned, so Render does not choose.
- **The test suite tripped its own rate limit.** Every test arrives from the same IP and
  registration is capped at five an hour, so the sixth signup failed with a 429 and cascaded into
  seven failures that looked nothing like their cause. `clearTestDatabase` now also resets the
  counters. Worth noting as a category: **process-global state added to the app becomes
  process-global state in the suite.**

## 6. What was verified

`server` has **220 passing tests**, up from 195. `client` builds clean.

New coverage: the memory store's windows, expiry and sweep; the middleware's headers, 429 and
per-subject budgets; login limiting end to end; the daily ceiling's arithmetic, per-day separation
and durability; the worker deferring rather than skipping and never calling the provider; the
reaper holding work back and resuming; the per-user cap including that a **re-save at the cap still
succeeds**, because a re-save creates nothing and refusing it is exactly the experience this
product exists to avoid; and the drain, including that `stop()` waits for a fetch in flight.

**And it was run, not just tested.** Docker was down on this machine, so MongoDB came from
`mongodb-memory-server` — a real mongod, just ephemeral — with everything else the actual boot path
in `NODE_ENV=production`. That run confirmed: health, helmet headers, the session cookie arriving
as `HttpOnly; Secure; SameSite=None`, an authenticated round trip, a save reaching `pending`,
`RateLimit-*` headers, the 21st save in an hour refused with 429, CORS allowing the configured
origin with credentials and not echoing an unknown one, and a **clean SIGTERM**: three in-flight
fetches completed after the shutdown began and before `Shutdown complete`, which is the drain
working where the unit tests can only claim it does.

Not verified, and only provisioning can: Atlas over the public internet, Render's actual SIGTERM
(the smoke test emits the signal in-process, because Windows terminates rather than signalling),
cold-start behaviour, and the real cross-site cookie in a browser.

## 7. Handover: what is left

Code is complete. These are dashboard steps, in order:

1. **MongoDB Atlas** — M0 cluster, database user scoped to `linkvault`, network access `0.0.0.0/0`
   (Render free has no static outbound IP; compensate with a long generated password). Same region
   as Render.
2. **Render** — web service, Root Directory `server`, build `npm ci`, start `npm start`, health
   check path `/api/health`. Environment variables per the list handed over with this change.
3. **Vercel** — project, Root Directory `client`, `VITE_API_BASE` set to the Render URL **including
   `/api`**. `client/vercel.json` already handles client-side routing.
4. **Back to Render** — set `CLIENT_ORIGIN` to the Vercel production URL once it exists. This is
   the one ordering trap: each side needs the other's URL, so the API gets deployed first with a
   placeholder and corrected after.
5. **Cron ping** on `/api/health` every 10 minutes. Render free spins down after ~15 idle minutes
   and takes ~50 seconds to wake; 750 instance-hours covers exactly one always-warm service.
6. **Verify end to end against the deployed instance.** Phases 3, 4 and 5 each produced bugs that
   only appeared against a real dependency. Assume this one will too.

## 8. Open questions this leaves

Unchanged from the plan: the Phase 6 embedding runtime, Atlas Vector Search on M0, and where Kafka
runs in production. Closed: whether Vercel meters external rewrites (no longer applicable).

New, and all consequences of decisions taken here:

1. **When Safari stops being acceptable.** The answer is the Bearer-token path, already planned and
   already scheduled after Phase 6. The question is only whether it gets pulled forward.
2. **Whether 200 enrichments a day is the right ceiling.** It is a guess priced at roughly $0.12 a
   day worst case. Real usage is the only thing that can correct it, and the counter documents are
   the record to read.
3. **Whether open registration survives contact with the internet.** The caps make abuse expensive
   rather than impossible. If it happens, closed registration is a small change and is still the
   strongest single protection available.
