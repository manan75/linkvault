# Phase 4 plan: Kafka and background workers (2026-08-30)

Agreed with the user before starting Phase 4. `CLAUDE.md` remains the source of truth for product
and architecture; this records the decisions it does not cover and the order the work should
happen in.

Scope per `CLAUDE.md` Phase 4: **Kafka, background workers, event-driven processing.**

---

## 1. Why Kafka, honestly

`CLAUDE.md` closes with "Do not blindly add technology because it appears in the architecture
diagram", so this gets the "Important Rule" treatment properly rather than pointing at the diagram.

**What problem it solves.** Phases 5 and 6 add two more processing stages to every saved link:
summary and tag generation, then embedding. Those stages have nothing in common with extraction.
Extraction is I/O-bound, cheap, and finishes in seconds. Embedding is compute-bound and needs a
Sentence Transformers model, which is Python. They need to scale independently, fail independently,
and — the part nothing in the current design can do — **run in different processes and different
languages**.

**Why the current architecture is insufficient.** The Phase 3 poller runs *inside the API process*.
It shares the API's lifecycle, its memory, and its runtime. Three consequences:

- Putting the embedding stage there would load a model into the API process.
- Scaling extraction would mean scaling the API, and vice versa.
- A Python process cannot participate at all.

**Alternatives considered.**

- *Keep MongoDB as the queue, add more poller processes — including Python ones.* This genuinely
  works, and it deserves more credit than it usually gets: the claim is already atomic, so N
  processes in any language can poll the same collection safely. Rejected for one specific reason
  rather than a vague one: **fan-out**. With a single `processingStatus` field the stages must be
  strictly linear, and each stage has to know which status the next stage waits on. With a log,
  `link.enriched` can feed the embedding worker *and*, later, a dead-link checker *and* a
  recommendation job, none of which need to know the others exist. That is the decoupling
  Principle 3 asks for, and it is the thing Mongo-as-queue cannot give.
- *A managed queue — SQS, RabbitMQ.* Simpler to operate. Rejected because it has no log semantics:
  no replay. Phase 6 will want to re-embed the entire corpus when the model changes, and with a
  queue that means writing a bespoke backfill job. With a log it is resetting a consumer offset.
- *Defer Kafka to Phase 6, when the Python worker actually arrives.* Tempting, and the poller would
  carry Phase 5 fine. Rejected because Phase 5 would then be built against the poller and rewritten
  a phase later. Introducing the transport now means summary and tag generation is written once,
  against the transport it will keep.

**Why this is appropriate.** Log semantics buy replay and fan-out, both of which are needed by
name in later phases. Keyed partitions give per-link ordering with real parallelism. And the
consumer shape is the shape the Phase 3 worker already has, so the migration is small.

## 2. Worker language split — decided

The open question carried since Phase 2. **Answer: all Kafka consumers are Node. Python appears
only as a stateless FastAPI embedding service, called over HTTP by a Node consumer.**

Why:

- **One Kafka client, one retry policy, one DLQ story.** Two languages consuming means two client
  libraries, two sets of consumer-group semantics, and two implementations of the same backoff
  ladder that already exists and is tested.
- **The Python part stays boring.** A stateless model server is easy to deploy, easy to scale
  horizontally, and easy to test — no consumer-group coordination, no offset management.
- **Batching survives.** The Node embedding consumer can accumulate N links and send them to
  FastAPI in one call, which is where nearly all the batching win actually is.

Trade accepted: the embedding service becomes a synchronous dependency of its consumer. If FastAPI
is down, the consumer retries and lag grows — which is the correct behaviour, just not as elegant
as backpressure at the model itself. **Revisit if throughput ever makes a native Python consumer
worth the second client library.** Phase 3 already nudged this way by writing extraction in Node;
this makes it explicit.

## 3. Topics

`CLAUDE.md` names five events. **Only create the ones something produces and consumes this phase:**

| Topic | Produced by | Consumed by | Phase |
| --- | --- | --- | --- |
| `link.created` | the reaper (§5) | metadata worker | **4** |
| `metadata.extracted` | metadata worker | nothing yet | **4** |
| `link.processing.failed` | any worker | nothing yet | **4** |
| `link.enriched` | enrichment worker | embedding worker | 5 |
| `embedding.created` | embedding worker | nothing | 6 |

`metadata.extracted` has no consumer in Phase 4 and is published anyway — it is what Phase 5
subscribes to, and publishing it now means Phase 5 adds a consumer without touching this code.

- **Key every message by `linkId`.** Per-link ordering is guaranteed, and partitions spread evenly.
  Keying by `userId` would serialise one user's entire queue behind their slowest link.
- **Three partitions**, so the consumer group can scale to three without repartitioning.
- **Replication factor 1** locally. A production value is a Phase 9 decision.
- One consumer group per worker type: `metadata-worker`.

## 4. Payloads carry the id, not the document

Messages carry `{ linkId, userId, occurredAt }` and nothing else. The consumer loads the link from
MongoDB.

The alternative — putting the whole bookmark in the message — makes the log the source of truth for
data MongoDB already owns, and guarantees the consumer sometimes acts on a stale copy of a document
the user edited in between. It also puts private bookmark content into a second durable store, which
Principle 8 gives no reason to do. `userId` rides along only so a consumer can log and scope without
a second read.

## 5. What publishes `link.created` — the dual-write trap

**Decided: the reaper is the only producer, at first.**

The obvious design is for the API to publish on save. It has a silent failure mode: the link is
committed to MongoDB, then the publish fails — broker down, process killed in between — and the
event never exists. The link sits at `pending` forever, with nothing logged and no error anywhere.
That is *exactly* the failure this project already hit once this session with the missing
`processingAttempts` field, and it was invisible both times.

The fix reuses what exists. The Phase 3 poller already sweeps MongoDB for links needing work; it
now publishes instead of processing. **This makes the `links` collection its own outbox** — no
outbox table, no Mongo transactions, no relay process.

To stop the reaper republishing the same link every sweep, one status is added:

```
pending  --reaper publishes-->  queued  --consumer claims-->  processing  -->  ready | failed
```

- Reaper: `findOneAndUpdate({ processingStatus: 'pending', … }, { $set: { processingStatus: 'queued', queuedAt: now } })`, then publish. **If the publish throws, set it straight back to `pending`.**
- A `queued` link older than a lease goes back to `pending` — that covers the process dying between
  the status write and the publish, and covers a message genuinely lost. This is the same
  stale-lease sweep already written for `processing`, pointed at a second status.
- **Retryable failures go back to `pending`, not `queued`**, so the existing backoff ladder still
  governs *when* a link is republished. The reaper becomes the retry trigger and no retry topic is
  needed.

Publish-on-save is a **latency optimisation to add afterwards**, doing the same
`pending → queued` + publish transition inside the request, with the reaper still sweeping behind
it. Until then the cost is a few seconds of latency on a background job, which nobody is watching.

## 6. Idempotency comes free

Kafka is at-least-once; Principle 4 requires consumers to tolerate redelivery.

The claim already does it. A consumer's first act is
`findOneAndUpdate({ _id, processingStatus: { $in: ['queued', 'pending'] } }, …)`. A redelivered
event for a link that is already `ready` matches nothing, claims nothing, and is acked. No
deduplication table, no processed-message log.

## 7. Failure handling

Unchanged from Phase 3, deliberately:

- The **backoff ladder stays in the document**. It is written, tested, and does not need a topic.
- **No retry topics and no DLQ topic.** `processingStatus: 'failed'` *is* the dead-letter store —
  and unlike a DLQ topic it is queryable, scoped per user, visible in the dashboard, and already
  has a retry endpoint.
- `link.processing.failed` is published on terminal failure for **observability only**. Nothing
  consumes it this phase.
- A poison message that crashes the consumer must not block its partition. Every handler is
  individually guarded, exactly as `runOnce` guards each link today.

## 8. Local development, and a problem worth naming now

**Kafka will require Docker on a machine that has so far not needed it.** The session notes record
that MongoDB runs as a native Windows service here and that `docker compose up -d` has never
actually been used. Kafka has no comparable native install worth having.

So: **`ENABLE_KAFKA=false` keeps the Phase 3 in-process poller path working.** Both paths share
`processLink` untouched — only the trigger differs, perhaps thirty lines — so this is a flag, not a
parallel implementation. It keeps the app runnable with no broker, and it makes the cutover
reversible. **Delete the poller path at the end of Phase 5**, once Kafka has been the real path for
a phase.

Compose gains a single-node `apache/kafka` in **KRaft mode — no ZooKeeper**. New env:
`KAFKA_BROKERS`, `KAFKA_CLIENT_ID`, `ENABLE_KAFKA`.

## 9. Testing

- **The 131 existing tests must keep passing untouched.** If migrating the trigger changes an
  assertion about extraction, something has been coupled that should not be.
- `processLink` is already transport-agnostic and stays unit-tested as it is.
- The producer/consumer wiring is tested against an **in-memory fake** implementing the two methods
  actually used. Enough to prove the reaper publishes what it claims and reverts on failure.
- **No broker in `npm test`.** One opt-in integration suite, run deliberately, not on every save.

## 10. Step plan

1. **Compose + config.** Single-node KRaft Kafka, env vars, `ENABLE_KAFKA` flag. Verify a topic can
   be produced to and consumed from before writing any application code against it.
2. **A thin client module** — `publish(topic, key, payload)` and `subscribe(topic, group, handler)`
   — with an in-memory implementation used by tests and by the flag-off path.
3. **The `queued` status**, `queuedAt`, and the stale-`queued` sweep. Tests first; this is the
   piece that makes lost messages recoverable.
4. **Poller becomes reaper**: claim `pending → queued`, publish `link.created`, revert on publish
   failure.
5. **Metadata worker becomes a consumer** of `link.created`. `processLink` is not touched.
6. **Publish `metadata.extracted` and `link.processing.failed`** at the terminal transitions.
7. **Split the worker into its own entrypoint** (`server/src/workers/index.js`), runnable as a
   separate process from the API, with its own Compose service. This is the point of the phase:
   until they are separate processes, nothing has actually been decoupled.
8. **Verification**: API and worker as separate processes; save links and watch them flow; kill the
   worker mid-fetch and confirm the stale-lease sweep recovers; stop the broker and confirm links
   accumulate at `pending` and drain when it returns.

## 11. Not in Phase 4

Summary and tag generation (Phase 5), embeddings and the Python service (Phase 6), Redis (Phase 7).
Also deliberately out: DLQ topics, a schema registry, exactly-once semantics, and consumer
autoscaling. And on the product side, **automatic collection allocation** — see below.

## 12. Automatic collection allocation — asked, and deferred

The user raised the busy-paster case: people paste a link and move on, so everything piles up in
Uncategorised. Worth recording what was decided and why, because it will come up again.

**Auto-tagging is already committed** — `CLAUDE.md` lines 9, 30 and 74, scheduled as Phase 5 "Tag
generation". So a user who never creates a collection still gets machine organisation: generated
tags, the existing tag sidebar and filters, and Phase 6 semantic search. Nothing is misfiled,
because nothing is filed.

**Automatic allocation into collections appears nowhere in `CLAUDE.md`.** The nearest entry is
"Advanced recommendations" under Future Features. Two arguments against adding it now:

- **Cold start.** Filing into an existing collection requires existing collections. The user who is
  too busy to file has none, so auto-assign-to-existing helps *organised* users go faster — a real
  benefit, but a different person than the one the question was about.
- **Silent misfiling is worse than not filing.** Uncategorised is at least predictable. A link that
  quietly lands in the wrong collection breaks "you'll find it later" for anyone browsing by
  collection. Search is unaffected, so the damage is narrow — but it is aimed at the exact promise
  the product runs on.

**Decision: revisit after Phase 5 ships**, with real auto-tagged links to judge against rather than
a guess. If it is added then, the ladder is: suggest-only from tag overlap → suggest from embedding
similarity to a collection centroid (Phase 6) → auto-assign above a threshold, opt-in and
reversible, only if suggestions prove reliable. **Uncategorised keeps its name**; the "Inbox"
reframe was offered and declined.

## 13. Still open after this phase

1. **Vector search in local dev** — needed before Phase 6. Atlas Local container, or a real Atlas
   cluster for development. Architectural, and deserves the "Important Rule" treatment.
2. **Where Kafka runs in production** — a Phase 9 question. Managed (Confluent, Redpanda, MSK) or
   self-hosted, and what that costs. Self-hosting a broker for a small app is usually the wrong
   trade, but that is a decision to make with real numbers.
3. **Whether the embedding service stays HTTP** — §2 decided yes; the trigger to revisit is
   throughput, not taste.
